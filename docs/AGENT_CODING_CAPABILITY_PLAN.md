# YOCIM AGENT — Coding 能力分析与提升计划

> 本文档只做分析与规划，不含代码改动。所有「现状」结论均可在下列文件位置核实，行号为撰写时（2026-11-16）的实际位置。
> 阶段完成后请就地更新 §6 的验收结果，不要另起交接文档。
>
> **状态：P0 已实现（2026-11-16）。** §2 描述的是 **P0 之前的基线**，用于说明问题来源；
> P0 的实际改动、与计划的偏差、以及仍未解决的缺口见 **§11**。

## 1. 结论先行

**一句话判断：YOCIM AGENT 目前是一个「带文件读写能力的对话助手」，还不是「能独立完成编码任务的 Coding Agent」。**

现有 Agent 循环（`src/main/agent/agentEngine.ts`）在工程结构上是干净且正确的：Provider 抽象、流式事件、abort 取消、工具结果回填、审计落库都齐备。问题不在架构，而在**工具接口的表达力**和**上下文的组织方式**：

| 缺口                                                       | 直接后果                                              |
| ---------------------------------------------------------- | ----------------------------------------------------- |
| 编辑只有「整文件覆盖」与「唯一文本匹配替换」               | 改 3 处就要 3 次调用 + 3 次审批；原文差一个空格就失败 |
| `read_file` 不给行号、不能分页                             | 模型无法锚定位置，只能整文件重写，容易误删无关代码    |
| 工具轮次上限 6，超出直接报错                               | 超过 6 步的任务必然中断，且中断后没有续跑机制         |
| 历史只回放 user/assistant 文本                             | 第 2 轮起模型就「忘了」第 1 轮读过什么，只能重复读    |
| 无计划/待办、无验证工具、无诊断                            | 改完没有「我改对了吗」的反馈通道，无法自我修正        |
| 已有资产（ripgrep / Git / 任务 / 调试 / 远程）未接给 Agent | 项目里最值钱的能力，Agent 一个都用不到                |

**最刺眼的一条**：`src/main/workspace/searchService.ts` 已经有一套完整的 ripgrep 搜索（正则、include/exclude、大小写、流式、远程支持），而 Agent 的 `search_files` 用的是 `workspaceTools.ts` 里自研的朴素子串遍历——纯文本、大小写不敏感、无正则、无 glob、扫 2000 个文件就停。**同一份代码库里存在两套搜索，Agent 用的是差的那套。**

第二个刺眼的事实：远程工作区（SSH）下，Agent 的所有文件工具直接抛 `E_UNSUPPORTED`（`workspaceService.ts:96`），因为 `runReadFile` / `runWriteFile` 走的是本地 `node:fs`。远程工作区面板能浏览、能编辑、能跑 Git，但 Agent 一句话都改不了。

## 2. 能力清单（事实基线）

### 2.1 工具面

`src/shared/tools.ts:5` 定义了全部 5 个工具，没有第 6 个。

| 工具           | 能力边界        | 关键限制（代码位置）                                                                                                                          |
| -------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_dir`     | 列目录树        | depth ≤ 3；树条目上限 500（`ipcChannels.ts:96-98`）；无 glob/ignore、无文件大小、无行数                                                       |
| `read_file`    | 读文本文件      | **无行号**、**无 offset/limit**、单次最多 2MB（`workspaceFs.ts:125`、`ipcChannels.ts:95`）——大文件一读就撑爆上下文                            |
| `search_files` | 子串搜索        | 无正则/glob/include/exclude；扫描上限 2000 文件、单文件 512KB、最多 200 条、无上下文行（`workspaceTools.ts:10-11`）                           |
| `write_file`   | 覆盖 / 单块替换 | 补丁模式要求 `oldText` **必须且只能匹配 1 次**（`workspaceTools.ts:140-143`）；一次调用只能改一处；无行号锚点、无模糊匹配、无多块补丁         |
| `run_command`  | 受控命令        | 白名单仅 `node/npm/npx/pnpm/yarn/tsc/vitest/git`，`git` 仅限 7 个只读子命令（`commandRunner.ts:7-17`）；无 python/pytest/cargo/go/make/dotnet |

### 2.2 循环与上下文

- **轮次**：`MAX_TOOL_ROUNDS = 6`（`agentEngine.ts:21`），第 7 轮直接 `E_TOOL_LIMIT` 报错（`agentEngine.ts:220`）。真实编码任务普遍需要 20–60 轮。
- **串行执行**：`for (const call of calls)` 顺序 `await`（`agentEngine.ts:183-212`），三个 `read_file` 也要排队。
- **历史裁剪**：`chat.ts:354-362` 只取最近 **50 条** user/assistant **纯文本**，工具调用与工具结果**全部丢弃**。这意味着多轮对话中，模型无法引用「上一轮我读过 `src/x.ts`」这一事实。
- **System Prompt**：仅 4 行（`agentService.ts:15-20`）——「你是编程助手 / 保持简洁 / 不要编造 / 用工具」。**没有**操作系统、工作区根路径、项目规则、工具使用策略、验证要求、输出格式。
- **无自动上下文**：当前打开文件、光标选区、最近改动需用户手动「添加到对话」（附件机制），Agent 自身不感知。
- **无 repo map / 代码索引**：模型进入陌生仓库只能靠 `list_dir` 一层层摸。
- **无项目规则文件**：不读 `AGENTS.md` / `.yocim/rules.md`，项目约定无法沉淀。

### 2.3 验证与反馈

- 命令输出**非流式**：`runWorkspaceCommand` 收完全部 stdout/stderr 才 resolve（`commandRunner.ts:120-185`）。跑 3 分钟测试，模型和用户前 3 分钟看不到任何东西。
- 输出上限 64KB，超时上限 300s。
- **无结构化验证工具**：没有 `run_tests` / `typecheck` / `get_diagnostics`。模型要判断「改对没改对」，只能自己 `run_command` 跑 `npm test`，然后从原始日志里肉眼找 `FAIL`。
- **主进程无 LSP/诊断**：全仓 grep 无 diagnostic/lsp 服务，Monaco 只活在 renderer。Agent 拿不到类型错误。

### 2.4 安全与可观测（这是当前最强项）

- 路径守卫（`pathGuard.ts`）：拒绝绝对路径、`..`、网络路径，`realpath` 后校验根内。
- 危险命令正则拦截 + 可执行白名单 + 最小环境变量（`commandRunner.ts:19-33,66-88`）。
- 审批三档（manual/auto/open，`toolService.ts:95-120`），挂起 Promise，取消即拒绝（`approvalManager.ts`）。
- 审计落 SQLite + 工具调用表；写入前自动快照，可时间线回滚（`toolService.ts:169-186`）。
- **这块不用大改，只需在细粒度上补强**（见 §5 P4）。

### 2.5 存量资产盘点（未被 Agent 使用）

| 已有能力                                              | 位置                           | Agent 能否用                             |
| ----------------------------------------------------- | ------------------------------ | ---------------------------------------- |
| ripgrep 全文检索（正则/glob/远程）                    | `workspace/searchService.ts`   | ❌ 用的是自研朴素版                      |
| Git 状态 / diff / 暂存 / 提交                         | `git/gitService.ts`            | ❌ 只能 `git status\|diff\|log` 原始输出 |
| 任务运行器（识别 npm/pnpm/yarn、`.yocim/tasks.json`） | `tasks/taskService.ts`         | ❌                                       |
| Node 调试（断点/变量/调用栈）                         | `debug/debugService.ts`        | ❌                                       |
| 远程执行（WSL UNC / SSH SFTP）                        | `remote/*`、`execRegistry.ts`  | ❌ SSH 下直接不可用                      |
| Monaco 编辑器 / 补全 / 诊断                           | renderer                       | ❌                                       |
| 时间线快照与回滚                                      | `workspace/timelineService.ts` | 仅写入后自动快照                         |

**结论：当前 Agent 是一座孤岛，主进程 90% 的工程能力它都碰不到。** 提升 Coding 能力最划算的动作，是把这些存量能力接进来，而不是从零造工具。

## 3. 成熟度评分

按 Coding Agent 的通用能力维度打分（1=缺失，3=可用但受限，5=业界水准）：

| 维度           | 分数 | 判据                                                                  |
| -------------- | :--: | --------------------------------------------------------------------- |
| 阅读与检索     |  2   | 能读能列，但无行号、无分页、搜索不支持正则/glob，大仓库基本不可用     |
| 编辑与补丁     |  2   | 只能整文件覆盖或唯一串替换，多块修改成本极高，易误伤                  |
| 执行与验证     |  2   | 能跑 7 类命令，但无流式、无结构化结果、无诊断、白名单过窄             |
| 上下文工程     |  1   | 无规则文件、无 repo map、无自动上下文、跨轮次丢失工具历史、无预算控制 |
| 规划与分解     |  1   | 无 todo/plan，靠模型在正文里自言自语                                  |
| 自主性与续跑   |  1   | 6 轮硬上限，超限即失败，不可续                                        |
| 安全与可控     |  4   | 路径守卫、命令拦截、审批、审计、回滚齐备，仅缺细粒度授权              |
| 可观测与可回滚 |  4   | 步骤时间线、审计面板、快照回滚都有                                    |

**综合 2.1 / 5。** 安全侧已达到可用水位（4），认知侧（上下文/规划/自主性）几乎是空白（1）——这正是"能聊天但不能干活"的典型画像。

## 4. 根因分析

五个结构性缺口，按杠杆从高到低：

1. **编辑原语太弱**（`write_file` 只能整文件或单块精确替换）。这是 Coding Agent 最核心的动作，接口表达力直接决定成功率。原文匹配失败率随文件规模线性上升，且无法一次改多处。
2. **工具结果不进历史**（`chat.ts:354`）。模型每轮从零开始，多轮重构任务必然反复读同一文件，既慢又容易改错（内存里的版本与磁盘不一致）。
3. **没有验证闭环**（无结构化测试/诊断工具 + 非流式输出）。模型无法自我修正，只能"改完就说好了"，正确性完全依赖一次成型。
4. **上下文没有任何组织**（无 rules、无 repo map、无预算）。模型不知道项目用什么框架、什么风格、禁止什么，只能猜。
5. **自主性被硬上限锁死**（6 轮）。即使前面四条都修好，复杂任务仍会在第 7 步断掉。

## 5. 提升计划

阶段划分原则：**先补工具表达力（P0），再补认知（P1），再补反馈闭环（P2），最后放开自主性（P3）**。前三个阶段各自都能独立产生可观测的能力提升，不需要等全部做完。

### P0 — 工具协议与编辑能力（最高优先级）

目标：让模型能在**不整文件重写**的前提下，精准完成多块修改，并在大仓库里高效定位。

| 编号 | 改动点                       | 要点                                                                                                                                                         |
| ---- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T0.1 | `read_file` 加行号与分页     | 返回带行号前缀的内容；新增 `offset`/`limit`（行），默认 limit=400；超限时明确提示「共 N 行，请用 offset 继续」；保留 2MB 硬上限但改为按行截断                |
| T0.2 | 新增 `edit_file`（多块补丁） | 参数为 `edits: [{ oldText, newText }]`，**一次调用原子应用多块**；任一块匹配失败则整体不落盘并返回失败块与上下文；匹配策略三级：精确 → 去首尾空白 → 行号锚点 |
| T0.3 | `write_file` 保留但收窄      | 仅用于新建文件与整文件重写；补丁场景引导到 `edit_file`                                                                                                       |
| T0.4 | `search_files` 换成 ripgrep  | 复用 `searchService.ts`，新增 `regex`/`glob`/`include`/`exclude`/`contextLines`；缺失 rg 时回退现有实现并标注 `engine`                                       |
| T0.5 | `list_dir` 增强              | 增加可选 `glob`、返回文件大小与行数；对 >500 条目返回「已截断，请用 glob 收窄」                                                                              |
| T0.6 | 工具描述重写                 | 描述里写清「何时用哪个」、行号语义、路径必须相对工作区根；当前描述过于简略                                                                                   |

**验收标准**

- 在 ≥3000 行文件上完成 5 处不连续修改：工具调用 ≤ 2 次，无需整文件重写。
- 同一任务若原文有 1 个字符偏差（缩进变化），`edit_file` 仍能定位成功（走降级匹配）。
- `search_files` 支持正则，结果含行号与上下文行，命中数与 ripgrep 面板一致。
- 单测覆盖：多块原子性（一块失败全不落盘）、降级匹配、分页边界。

### P1 — 上下文工程

目标：让模型"知道自己在哪个项目里干活"，并且多轮对话不丢记忆。

| 编号 | 改动点             | 要点                                                                                                                                                                                                                 |
| ---- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1.1 | 重写 System Prompt | 分段：① 身份与角色 ② 环境（OS、工作区根、是否远程）③ 项目规则（见 T1.2）④ 工具使用策略（先搜索后读取、改动前先读、验证后再收尾）⑤ 编辑规范（最小改动、保留风格、不加无关注释）⑥ 收尾要求（说明改了什么、验证了什么） |
| T1.2 | 项目规则文件       | 支持 `AGENTS.md` 与 `.yocim/rules.md`，按优先级合并，注入上限 8KB，超限截断并提示；工作区切换时重新加载                                                                                                              |
| T1.3 | 工具历史回放       | DB 新增工具调用序列（已有 `tool_calls` 表可复用），重建时把 assistant(toolCalls) + tool 结果按原顺序回放；单条工具结果超过 2KB 时存"摘要 + 关键行"，原文按需重读                                                     |
| T1.4 | 上下文预算与裁剪   | 估算 token（粗粒度 char/4 即可），超阈值按优先级裁剪：附件 > 陈旧工具结果 > 早期对话；裁剪行为要可见（UI 标注"已压缩 N 条历史"）                                                                                     |
| T1.5 | 自动上下文注入     | 每轮注入：当前打开文件路径与语言、光标选区（若在编辑器内）、当前工作区 Git 分支与脏文件列表（≤10 条）；作为独立 system 段落，无需用户手动添加附件                                                                    |
| T1.6 | repo map（轻量版） | 不引入 tree-sitter：用 `list_dir` + 扩展名过滤生成「目录 → 主要文件 → 顶层符号（正则提取 export/function/class）」的压缩索引，上限 4KB，工作区打开时缓存                                                             |

**验收标准**

- 连续 10 轮修改同一模块，第 10 轮仍能正确引用第 1 轮读过的文件内容，无需重复读取（用 mock provider 断言 messages 中工具结果存在）。
- 新建 `AGENTS.md` 写入"禁止使用 any"，Agent 生成的代码遵守该约束。
- 10 万 token 级上下文不报错，裁剪有明确 UI 提示。

### P2 — 验证闭环

目标：让模型能"改完自己验"，并看见过程。

| 编号 | 改动点                            | 要点                                                                                                                                                                                             |
| ---- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T2.1 | 命令白名单可配置                  | 保留危险正则拦截；白名单改为「内置默认 + 项目级 `.yocim/commands.json` + 设置页自定义」，默认补 `python/pytest/cargo/go/make/dotnet/gradle`；`git` 放开只读类（`diff --stat`、`show`、`log -n`） |
| T2.2 | 命令输出流式                      | 新增 `tool:output` 事件（携带 partial 文本），UI 在步骤卡内增量展示；主进程 300ms 节流合并                                                                                                       |
| T2.3 | `run_tests` 工具                  | 参数 `pattern`/`watch=false`；自动识别 test runner（vitest/jest/pytest/go test）；**只回结构化摘要**：总计/通过/失败数 + 失败用例名 + 失败断言前后 5 行，不把全量日志塞进上下文                  |
| T2.4 | `run_typecheck` / `run_lint` 工具 | 复用 `tsc --noEmit` 与 eslint，按文件聚合错误，输出 `file:line:col message` 紧凑格式，上限 50 条                                                                                                 |
| T2.5 | `get_git_diff` 工具               | 复用 `gitService`，返回当前未提交 diff（可限路径），让模型在收尾前自审改动                                                                                                                       |
| T2.6 | 诊断桥（可选，后置）              | 通过 renderer 的 Monaco 拿 marker，经 IPC 回传主进程，作为 `get_diagnostics` 数据源；若成本过高，先用 T2.4 的 tsc 代替                                                                           |

**验收标准**

- 给一个失败单测，Agent 从「跑测试 → 读到失败用例 → 改代码 → 复跑通过」≤ 4 轮，且上下文中不含全量测试日志（< 3KB）。
- 3 分钟测试运行期间，UI 每 300ms 可见新输出，可中途取消。

### P3 — 规划与自主性

目标：让 Agent 能承接"多步骤、多文件"的任务，而不是一问一答。

| 编号 | 改动点                 | 要点                                                                                                                       |
| ---- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| T3.1 | `update_plan` 工具     | 模型维护结构化待办 `[{step, status}]`；UI 渲染计划卡（pending/doing/done）；每轮强制回传当前计划，形成"计划-执行-勾选"闭环 |
| T3.2 | 轮次上限分级           | 按任务类型配额：问答 6 / 单文件修改 20 / 多文件任务 60；达上限不报错，改为「暂停并询问是否继续」（可续跑，run 状态持久化） |
| T3.3 | 只读工具并行           | `read_file`/`search_files`/`list_dir` 并发（上限 4），写工具与命令保持串行；事件序仍保证 seq 单调                          |
| T3.4 | 子代理（可选，最后做） | explore（只读调研）/ implement（写）/ verify（跑测试）三角色，仅在轮次 > 30 的长任务启用；不引入独立进程，同进程不同工具集 |

**验收标准**

- 跨 5 个文件的重构任务（重命名导出 + 更新引用 + 跑测试）一次会话完成，成功率在基准集上 ≥ 70%。
- 计划卡随执行实时更新，中断后可恢复。

### P4 — 审批与体验（细粒度补强，不重做）

| 编号 | 改动点                  | 要点                                                                                                                  |
| ---- | ----------------------- | --------------------------------------------------------------------------------------------------------------------- |
| T4.1 | diff 预览审批           | 审批卡内展示 hunk（增删行着色），而非当前的一行 `argsSummary`                                                         |
| T4.2 | 会话级 / 项目级允许规则 | 「本次会话允许 `npm test`」「本项目允许写入 `docs/**`」；规则持久化，审计记录命中的规则名；危险正则拦截不可被规则绕过 |
| T4.3 | 批量审批                | `edit_file` 的多块补丁按一次审批处理（一次 diff 预览含多个 hunk）                                                     |
| T4.4 | 写前预检                | 写入前校验「文件在审批期间是否被外部修改」（已有冲突检测能力，扩展到 Agent 写入路径）                                 |

**验收标准**：一次典型「改 3 个文件 + 跑测试」任务，审批弹窗 ≤ 3 次。

### P5 — 评测与回归

没有度量就没有提升。P0–P3 每完成一项，都要能回答"到底强了多少"。

| 编号 | 改动点     | 要点                                                                                                                  |
| ---- | ---------- | --------------------------------------------------------------------------------------------------------------------- |

### 11.3 与计划的偏差

1. **远程（SSH）只覆盖搜索，未覆盖读写。** 计划里写的是「P0 起接口设计成可远程」，接口层已按此实现（`ToolFileIo` 单一入口），但 `read_file` / `edit_file` / `write_file` 在 SSH 工作区仍会报 `E_UNSUPPORTED`。
   补法很直接：新增 `createRemoteToolFileIo(sftp, root)` 基于 `remoteFs.readRemoteFile/writeRemoteFile`，在 `ipc/index.ts` 里按 `workspaceService.currentRemote()?.kind === 'ssh'` 注入。**不做**的原因是本机没有可用 SSH 服务器，写入路径无法真机验证，宁可留空也不要塞一段没跑过的写文件代码。
2. **`edit_file` 没有 `replaceAll`。** 同一段文本出现多次时直接报错并列出候选行号，要求模型补充上下文。理由：批量替换有误伤风险，且属于 P2 批量替换能力的范畴。
3. **`list_dir` 行数统计有条件。** 文件数 > 40 或单文件 > 32KB 时只给大小不给行数，避免一次列目录读几十个文件。计划里没写这个上限。
4. **快照语义未改。** Agent 写入后仍只生成「写入后」的 `agent` 快照，无法回滚到写入前（历史遗留行为，`toolService.snapshotAfterWrite`）。修它要动时间线语义与既有测试，留给 P4。

### 11.4 仍未解决的问题（按优先级）

1. 工具结果仍不进历史（`chat.ts:354` 只回放 user/assistant 文本）——P1 第一项，影响最大。
2. 轮次上限仍是 6，多文件任务会在第 7 步断掉——P3。
3. 无计划/待办、无结构化验证工具、无诊断——P2/P3。
4. SSH 下 Agent 只能搜不能改——P1 补 `createRemoteToolFileIo`（见 §11.3 第 1 条）。
5. 审批卡仍只有一行摘要，没有 diff 预览——P4。

### 12.2 关键决策与偏差

1. **上下文所有权移到主进程。** renderer 的 `history` 参数保留但只做旧会话迁移；压缩、用量、工具结果回放都以 `agent_context` 为准。UI 聊天记录（`messages` 表）不受压缩影响，压缩在会话内以系统提示形式可见。
2. **token 估算是启发式**（CJK ≈ 1 token/字，其余 ≈ 4 字符/token，每条消息 +4 开销）。偏保守（多估），宁可提前压缩也不爆窗口；不做真实分词。
3. **摘要走当前模型**，60s 超时，失败/摘要不比原文短时用确定性回退。压缩期间若正在生成回复，手动压缩会被拒绝（`E_CONFLICT`）。
4. **SSH 工作区不注入 repo map**（无本地 fs），system prompt 明确告知"文件工具暂不可用，请走 run_command"。
5. 编辑器**选区未进 contextHint**（需要 Monaco 选区状态上浮，成本/收益暂不划算）——选区仍通过「添加到对话」作为附件传递。
